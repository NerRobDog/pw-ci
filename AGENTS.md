## 1. Что за проект

Nival открыл боевую (battle) часть MOBA Prime World. Владелец проекта — Nik,
GitHub `NerRobDog`. Цели, в порядке приоритета:

1. Собрать клиент под macOS / Apple Silicon: сейчас через CrossOver/Wine,
   дальше — нативно.
2. **Заменить старый сетевой стек на современный, а не воспроизводить его.**

   оверлейные сети (ZeroTier, Tailscale, Radmin VPN), бои против ботов.
   Мотивация — сохранить игру на память и играть с друзьями.
4. Отдать наработки сообществу так, чтобы другие форки могли их переиспользовать.

## 2. Разделение кода: правило раскладки

Долгосрочный замысел — два репозитория с разными лицензиями:

| Репозиторий | Содержимое | Лицензия |
|---|---|---|
| инструментальный | CI, docker-compose локального серверного стека, лаунчер, генератор `server_ip.h`, патчи тулчейна, скрипты оверлейной сети, **новый сетевой стек**, извлечённое описание протокола | MIT, собственный код владельца |
| игровой | патчи к боевому коду, форк Prime World | лицензия Nival, некоммерческая |

Зачем: (1) инструментальная часть — собственный код под OSI-одобренной
лицензией, лицензия Nival не годится ни для чего, требующего открытой
лицензии; (2) чужие форки берут MIT-часть без юридической возни; (3) при
отзыве лицензии Nival инструментальная половина выживает.

**Решение владельца по срокам: формальное разделение — не сейчас, а когда
сборка станет хоть как-то играбельной.** Не предлагай и не выполняй
преждевременное разделение. Вместо этого соблюдай дешёвую страховку —
дисциплину каталогов, при которой будущее разделение сведётся к
`git filter-repo --path`, а не к ручной распутке истории.

### Раскладка каталогов

В `pw-ci` (всё здесь — собственный код владельца, будущий MIT):

```
pw-ci/
  .github/workflows/   # CI (сейчас: build.yml — ночная сборка клиента)
  ci/                  # скрипты сборки и патчи тулчейна, выносимые из workflow
  netstack/            # новый сетевой стек — свой код с нуля
  launcher/            # лаунчер, генератор server_ip.h
  stack/               # docker-compose локального серверного стека
  overlay/             # скрипты настройки ZeroTier / Tailscale / Radmin
  docs/
    protocol/          # извлечённая спецификация протокола и стейт-машин (раздел 4)
    superpowers/       # спеки и планы (домашняя конвенция)
  AGENTS.md, README.md
```

В форке `NerRobDog/Prime-World` — только правки внутри `pw/branches/r1117`
(код Nival, лицензия Nival).

### Правило: куда класть новый файл

Задай себе один вопрос: **содержит ли файл код Nival или производную от него
(дифф с контекстом, скопированный заголовок, фрагмент)?**

- Да → коммит только в форк `NerRobDog/Prime-World`, внутрь
  `pw/branches/r1117`. В pw-ci таким файлам места нет.
- Нет (свой код, скрипт, документация, описание протокола своими словами) →
  pw-ci, в соответствующий каталог верхнего уровня.
- Пограничный случай — правка, которую CI применяет к дереву сообщества:
  оформляй как **текстовую замену в скрипте** (как сейчас делает `build.yml`
  через `-replace`), а не как .patch-файл с контекстными строками кода Nival.
  Если без полноценного диффа не обойтись — это коммит в игровой форк.
- Никогда не копируй содержимое `pw/branches/r1117` в pw-ci — ни файлы, ни
  каталоги, ни «временно для удобства».

## 4. Старый серверный код = спецификация

Режим работы: **прочитать → зафиксировать знание текстом → выбросить код**.

Извлечённое знание о протоколе — это текст владельца, он переживёт отзыв
лицензии Nival. Требования к фиксации:

- Хранить в `pw-ci/docs/protocol/`, по файлу на подсистему
  (`handshake.md`, `session-state-machine.md`, `relay-transport.md`,
  `matchmaking.md`, ...).
- Писать **своими словами**: форматы сообщений — таблицами полей
  (имя, тип, размер, семантика), стейт-машины — списками состояний и
  переходов. Допустимы указания на источник вида
  `Src/Server/RdpTransport/<файл>:<строка>` — путь и номер строки не являются
  кодом.
- **Не вставлять фрагменты кода Nival** в эти документы — иначе документ
  станет производной работой и попадёт под лицензию Nival, что убивает весь
  смысл раздела.
- Каждый документ начинается с блока «что проверено, что предположение» —
  протокол восстанавливается чтением, а не отладкой живого сервера, ошибки
  неизбежны.

Отправные точки чтения: `Src/Server/RdpTransport` (транспорт),
`Src/Server/NetworkAIO` и `Src/Server/RPC` (обвязка), `Src/Server/Relay`
(доставка команд боя), `Src/Server/MatchMaking` + `Src/Server/Coordinator`
(жизненный цикл сессии), `Src/Server/NewLogin` + `Src/Server/UserManager` +
`Src/Server/ZZima` (авторизация — нужна только чтобы понять, что именно
заглушать).

## 5. Автономный запуск (без центральных серверов)

Составляющие, в порядке «дешевле → дороже»:

1. **Локальная игра с ботами уже работает без сети** — см. README апстрима:
   `Profiles/game.cfg`: `local_game 1`; в `private.cfg` (переименовать из
   `private.cfg_example`) после `AT BEGINNING GAME` добавить строку
   `add_ai bots`. Это базовый сценарий, который CI-сборка обязана не сломать.
2. **`server_ip.h`** — файл не версионируется (в локальном клоне
   `/Users/nik/ow2/prime-world` отсутствует; проверено). Он хардкодит
   `SERVER_IP`, `SERVER_IP_W_ARRAY`, `SESSION_TOKEN`, `API_KEY`, порты. Наш
   CI (`.github/workflows/build.yml`) генерирует заглушку в
   `Src/PW_Game/server_ip.h`: все адреса `127.0.0.1`, токены `"offline"`.
   Для LAN-игры достаточно подставить адрес хоста сессии — это задача
   генератора в `launcher/`, не правка кода игры.
3. **Заглушки авторизации.** `NewLogin`, `UserManager`, `ZZima` завязаны на
   мёртвую центральную инфраструктуру. Для автономного входа в бой их
   функции сводятся к «выдай игроку id и пусти в сессию» — это место замены
   новым стеком, а не починки. У сообщества роль моста выполняет
   `Client-Synchronizer-Server` из prime-world-classic — изучи его перед
   проектированием своего.
4. **`Db`** — открытый вопрос: не проверено, какой минимум персистентности
   нужен боевой сессии (талант-билды приходят с клиентом или ждутся от
   сервера?). Выяснить чтением `Src/Server/Db` и логики старта боя до
   проектирования заглушки.
5. **Оверлейные сети работают без правок в игре**: ZeroTier/Tailscale/Radmin
   дают участникам плоские unicast-IP в одной виртуальной L2/L3-сети — для
   игры это неотличимо от LAN. Никакого NAT-пробива в клиенте, никаких
   изменений протокола. Скрипты подготовки — `overlay/`, в игру не лезут.

## 6. Боты

Код ИИ героев существует и лежит в `pw/branches/r1117/Src/PF_GameLogic/`
(проверено): `PFSeriesAIController.cpp`, `PFAIStates.cpp`, `PFAIHelper.cpp/.h`,
`PFAIContainer.cpp`, `PFBaseAIController.cpp`, `PFMicroAI.cpp`, компонент
`AI.component`, каталог `AIWorldFacets/`. Признак бота — `PFPlayer.h:84`:
`bool const IsBot() const { return userID == -1; }`. Включение — консольная
команда `add_ai bots` (см. раздел 5).

Что это даёт: полноценные матчи без живых оппонентов — сборка остаётся
играбельной для одного человека, а LAN-матчи можно добивать ботами до полных
команд. Ботовый сценарий — обязательный smoke-тест каждой сборки.

Не подтверждено локально: флаги `isBot`/`bBot` в `PFHero.cpp` из постановки
задачи grep-ом не нашлись (0 совпадений) — признак бота реализован через
`userID == -1`. Не выдумывай несуществующие флаги.

## 7. Тулчейн и CI

- Основной солюшен: `pw/branches/r1117/Src/PF.sln`, Visual Studio 2008 SP1.
  Рабочие конфигурации: `ShippingSingleExe` (публичная) и `ReleaseSingleExe`
  (с читами) — обе присутствуют в PF.sln (проверено).
- **Тулчейн жёстко VC9 / Windows SDK 7.0-7.1. Современный компилятор взять
  нельзя**: в `Vendor/` лежат предсобранные библиотеки под VC9 — boost 1.46.1
  с суффиксом `-vc90-` (`Vendor/boost/stage/lib/`), ACE (`Vendor/ACE_wrappers`)
  и другие. C++ ABI между версиями MSVC несовместим; пересборка всего Vendor
  современным компилятором — отдельный большой проект, не смешивать с текущими
  задачами.
- Что делает CI (`.github/workflows/build.yml`, ночной cron 02:30 UTC +
  ручной dispatch, `windows-latest`):
  1. sparse-checkout `Prime-World-Classic/prime-world-classic`
     (`Src`, `Vendor`, `Tools`, `Data/GameLogic`, LFS);
  2. собирает VC9-тулчейн из ISO WDK 7.1 + VS2008 Express + SDK 7.1
     (archive.org), извлечение через lessmsi, кэшируется в `C:\vc9`;
  3. патчит `Src/CMakeLists.txt` текстовыми заменами (вырезает отсутствующие
     в опубликованном дереве файлы), генерирует заглушки `server_ip.h` и
     Steam-заголовков (редистрибуция Steamworks SDK запрещена), фиксит пару
     багов компиляции;
  4. сборка CMake 3.16 + jom (`NMake Makefiles JOM`), Release;
  5. артефакт `PrimeWorld-Release` (`PrimeWorld.exe` + dll).
- Меняя workflow, сохраняй паттерн «правки кода Nival — только текстовыми
  заменами на лету» (раздел 2) и кэш-ключи тулчейна (пересборка `C:\vc9`
  стоит ~десятки минут).

## 11. Открытые вопросы (задать владельцу, не решать самовольно)

1. **Путь `server_ip.h`**: в постановке упомянут `pw/branches/r1117/Srv/PW_Game`,
   но каталога `Srv/` в локальном клоне нет (проверено) — в CI заглушка
   кладётся в `Src/PW_Game/server_ip.h`. Уточнить фактический путь и полный
   набор макросов в prime-world-classic.
2. **Технология нового сетевого стека** не выбрана: язык, транспортная
   библиотека (ENet / GameNetworkingSockets / своя поверх UDP), граница
   интеграции с клиентом (замена `RdpTransport` на уровне линковки или
   внешний прокси-процесс а-ля Client-Synchronizer-Server).
3. **`Db`**: минимально необходимая персистентность для боевой сессии
   (источник талант-билдов и статов) — требует чтения кода.
4. **Отношения с prime-world-classic**: контрибьютить фиксы им или копить в
   своём форке; синхронизация с их `Client-Synchronizer-Server`.
5. **Критерий «хоть как-то играбельно»** для момента разделения репозиториев
   — сформулировать проверяемо (например: LAN-матч 2+ живых игроков + боты
